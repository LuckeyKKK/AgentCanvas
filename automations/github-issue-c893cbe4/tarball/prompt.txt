【步骤 1：理解问题】

读取 Issue 的：

- 标题
- 正文
- 评论
- 标签
- 关联链接
- 作者

同时浏览仓库的：

- README
- 贡献指南
- 目录结构
- 相关代码
- 近期提交
- 相关 Issue

理解项目和问题背景后再进行判断。

【步骤 2：查重】

检索本仓库全部 open 和 closed Issue，排除当前 Issue。

综合比较：

- 标题
- 正文
- 错误信息
- 复现步骤
- 影响模块
- 根因
- 预期结果

只有核心问题、根因或所需修复实质相同才判定重复。

仅关键词相似，或者处于相同模块但诉求不同，不算重复。

优先引用最早、信息最完整或已有解决方案的 Issue。

如果确认重复：

1. 先发布中文评论，包含：

   <!-- openhands-issue-triage:v2 -->

2. 评论同时包含：

   - 原 Issue 的编号和链接
   - 判定重复的依据
   - 如果原问题已经解决，概括解决结果

3. 评论成功后关闭当前 Issue。

4. 评论失败不得关闭 Issue。

5. 结束当前 Issue 的处理：

   - 不添加其他分类标签
   - 不分配负责人
   - 不做初审
   - 不添加 openhands
   - 不进入问题解决流程

重复 Issue 因为已经关闭，无需移除 needs-triage。

【步骤 3：来源标签】

仅处理非重复问题。

创建来源必须二选一：

- 如果 Issue 已有 auto-generated，保留它，不添加 human-generated。
- 如果没有 auto-generated，默认视为人工创建，添加 human-generated。
- 如果两个来源标签同时存在，不删除任何标签；将其视为阻塞，按照“统一阻塞处理”评论并 @S-zhi，然后停止处理当前 Issue。

【步骤 4：需求类型】

根据主要验收目标二选一：

- product-analysis：用户体验、业务规则、产品能力、交互、需求定义和使用流程等产品问题。
- technology-analysis：实现、缺陷、性能、安全、基础设施、重构、兼容性和测试等技术问题。

混合问题按照主要验收目标选择。

如果无法可靠判断：

- 不得同时添加两个标签
- 按照“统一阻塞处理”评论并 @S-zhi
- 停止处理当前 Issue
- 不添加 openhands

如果已经同时存在两个需求类型标签，视为冲突阻塞，不删除标签。

【步骤 5：难度和负责人】

Citizen L1：

- 大型或高难任务
- 跨核心子系统的架构变化
- 重大安全或权限问题
- 重大并发一致性问题
- 破坏性数据迁移
- 重大性能风险
- 根因高度不确定
- 需要复杂设计取舍
- 负责人设置为 S-zhi
- 不添加 openhands，不自动进入问题解决流程

Citizen L2：

- 目标明确且风险可控
- 涉及多个文件或模块
- 需要较多测试和兼容处理
- 代码修改篇幅较大
- 负责人设置为 LuckeyKKK
- 分审成功后添加 openhands，自动进入问题解决流程

Citizen L3：

- 局部、低风险、方案清晰
- 修改文件和代码量较少
- 不需要复杂迁移或架构决策
- 负责人设置为 feng978744573-netizen
- 分审成功后添加 openhands，自动进入问题解决流程

整体分配比例以当前自然月已分审 Issue 为统计范围：

- L1 最多约 10%
- L2 最多约 30%
- L3 约 60%～70%

L2 与 L3 可以动态调整。

任务所需能力优先，绝不能为了满足比例而把高风险任务降级。样本不足 10 个时允许暂时波动。

添加一个对应难度标签并设置对应 Assignee。

如果已有冲突难度标签、负责人不是仓库可分配成员或 API 拒绝，按照“统一阻塞处理”执行，不添加 openhands。

【步骤 6：问题初审】

默认通过。

以下情况通常不构成阻塞：

- 描述不够完美
- 一般实现风险
- 需要常规测试
- 修改量较大

只有以下情况才判定严重阻塞：

- 方案存在严重逻辑错误
- 存在重大数据或安全风险
- 需求自相矛盾且无法实现
- 必须先完成关键验证才能安全推进

标签和负责人操作成功后，发布一条中文初审评论，必须包含：

<!-- openhands-issue-triage:v2 -->

- 查重结果：未发现明确重复问题，并简述检索范围
- 创建来源：auto-generated 或 human-generated
- 需求类型：product-analysis 或 technology-analysis，并说明理由
- 难度等级：Citizen L1、Citizen L2 或 Citizen L3，并说明范围和风险依据
- 负责人：@对应账号
- 初审结论：通过或严重阻塞
- 初审建议：一条具体、可执行的建议
- 可能阻塞点：1～3 项；没有则写“暂未发现严重阻塞点”

如果初审为严重阻塞，评论第一行必须写：

@S-zhi 当前 Issue 存在严重阻塞，请介入处理。

随后停止当前 Issue 的处理：

- 保留 needs-triage
- 不添加 openhands
- 不进入问题解决流程

【步骤 7：交接到问题解决流程】

只有非重复、无阻塞、初审通过，并且标签、负责人和初审评论全部操作成功的 Issue，才能进入后续问题解决流程。

如果难度是 Citizen L2 或 Citizen L3：

1. 确认 Issue 状态仍为 open。
2. 确认难度标签和 Assignee 已正确设置。
3. 确认中文初审评论发布成功。
4. 添加 openhands 标签。
5. 重新读取 Issue，确认 openhands 已成功添加。
6. openhands 添加成功后，移除 needs-triage。

必须最后添加 openhands，因为该标签会触发后续问题解决流程。

如果添加 openhands 失败：

- 不得移除 needs-triage
- 不得声称交接成功
- 在运行日志中记录失败原因
- 后续定时运行只重试 openhands 交接，不重复发布初审评论

如果难度是 Citizen L1：

- 不添加 openhands
- 不触发自动问题解决
- 初审评论成功后移除 needs-triage
- 等待 S-zhi 人工处理
