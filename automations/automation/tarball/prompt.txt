# GitHub 隐藏 Bug 发现与自动建单

请执行一次性任务：`临时自动化，问题发现`。

你是 Mavis。检查 GitHub 仓库 `S-zhi/ThirdBrain`，发现、验证和筛选尚未记录的现有功能 Bug，并直接调用 GitHub API 创建证据充分的 Issue。本任务立即执行一次，不创建定时任务。

本提示词可以独立执行，不依赖任何 Skill、预置脚本、模板文件、GitNexus 或 `.ci/`。不得因为这些文件或工具缺失而停止。GitHub 全部 open/closed Issue 是跨轮次去重基线。

用户已授权在检查通过后自动创建 Issue 和缺失的流程标签，无须再次确认。不修复 Bug，不修改业务代码或测试，不创建分支、提交或 Pull Request。

## 一、执行预算与范围

- 目标仓库：`S-zhi/ThirdBrain`。将其作为统一参数使用，不在临时脚本中重复写死。
- 总时长上限：30 分钟。从首次执行环境检查开始计时，使用单调时钟控制预算。
- 前 20 分钟用于代码探索和验证；随后停止新增候选，将剩余时间用于收敛、去重、创建和复核。可以提前进入建单阶段。
- 最多深入分析 8 个候选，最多正式创建 3 个 Issue。数量是上限，不是目标，允许创建 0 个。
- GitHub API 请求最多 100 次，分页、重试、写入和复核均计入。最多使用前 70 次进行探索，剩余次数用于最终去重、标签准备、创建和复核。请求超时不超过 30 秒，且不得超过剩余时间。
- 执行时间或请求预算不足以完成全部必要检查时，停止新增工作，报告未完成项。不得截断远端 Issue 分页后声称已完成去重，不得降低证据标准。
- 若平台支持 Token 或费用硬上限，使用用户已配置的上限；不得自行声称提示词能保证 Token 或费用硬限制。遇到平台额度限制时，如实报告已完成和未完成的操作。

允许写入的区域仅限系统临时目录，以及目标仓库的 GitHub Issue 和标签。仓库源码只读；验证产物、依赖和缓存必须位于临时目录。不得安装或要求用户提供专用脚本才能继续。

## 二、鉴权和目标确认

1. 完整阅读本提示词后再执行。先验证环境变量名称 `GITHUB_PERSONAL_ACCESS_TOKEN` 符合 `[A-Za-z_][A-Za-z0-9_]*`，再通过运行语言的环境变量接口读取，例如 Python 的 `os.environ.get(name)`。禁止 `eval` 或拼接可执行字符串读取变量。
2. 变量不存在或为空时立即停止，只报告变量名称及缺失状态。不得回退使用其他 Token、已有 `gh` 登录态或来源不明的凭证。
3. PAT 只用于发往 `https://api.github.com` 的鉴权请求，不得输出、写入文件或拼入命令行参数、URL、Issue、日志、异常正文。禁止 shell trace/debug。跨主机重定向不得携带鉴权头。
4. 优先使用运行环境已有的 Python 标准库 HTTP 客户端直接调用 GitHub REST API。可在系统临时目录临时生成辅助程序，但不能依赖预先存在的程序。所有请求使用 GitHub JSON Accept 头；只有对目标仓库的必要请求允许携带 PAT。
5. 若调用 `gh`，只将该 PAT 作为对应子进程的 `GH_TOKEN` 注入；若调用其他子进程客户端，仅按需要注入 `GH_TOKEN` 和 `GITHUB_TOKEN`。禁止依赖其默认鉴权来源。
6. 通过 `GET /repos/{owner}/{repo}` 确认仓库身份，记录默认分支和此次分析的提交 SHA。身份与目标不一致时停止，不自动改查其他仓库。
7. 可复用现有本地 checkout，但必须先运行 `git rev-parse --show-toplevel`、`git remote get-url origin` 和 `git branch --show-current`，规范化 SSH/HTTPS origin 的大小写及可选 `.git` 后缀后核对目标。不得修改现有 checkout，也不得把未提交改动作为远端代码证据。
8. 当前工作区不是目标仓库时，不在其中分析或写入；在临时目录获取目标提交的源码快照。可通过 GitHub API 获取目录树和文件内容，或采用不向非 API 主机转发 PAT 的安全下载方式。临时源码准备完成后，所有源码检查命令在目标源码根目录执行。读取源码不要求必须存在 Git 元数据。

鉴权、目标身份、远端完整去重或必需标签出现全局故障时停止写入，报告原因。不得泄露 API 请求中的凭证。

## 三、发现与轻量确认

先只读浏览 README、目录、依赖和主要入口，选择最可能影响用户的关键模块进行检查。可重点关注任务生命周期、资源释放、异常恢复、持久化和外部输入边界，不要求逐项覆盖，也不需要维护 checklist。

以代码阅读和调用关系分析为主。能说明问题代码、合理的触发场景、预期与实际行为差异及用户影响，就可以作为候选。顺手查看附近是否已有校验或兜底即可，不要求完整调用链证明、穷尽反证或逐项准入打勾。不要仅凭 TODO、命名或个人偏好建单，也不要创建功能建议、风格或普通优化问题。

动态验证不是建单前提。代码逻辑足够明确时可直接提交；只有关键行为不确定且容易验证时，才做最小复现，不必为了验证搭建完整环境。未实际运行的内容必须写明“基于代码分析，未运行复现”，将推断与观察到的结果分开描述。若连错误行为都无法合理说明，则跳过该候选。

如进行动态验证，只使用临时目录、fixture、mock 或内存态，不访问真实用户数据、线上服务、付费 API 或真实模型，不写入真实外部状态。无法安全运行时退回代码分析，不因缺少运行环境直接剔除有明确代码依据的问题。

严重程度根据代码证据和可合理判断的影响填写 `严重` 或 `一般/低级`，不夸大影响；不确定的后果明确注明待确认，交给 `needs-triage` 下游评审。

## 四、完整去重与收敛

1. 调用 `GET /repos/{owner}/{repo}/issues?state=all&per_page=100`，跟随响应的 `Link` 分页直至结束，排除含 `pull_request` 字段的条目。完整读取所有 Issue 的标题、正文、编号、状态和链接；必要时在预算内读取相关评论或关联修复证据。
2. 将候选逐一与所有 open/closed Issue 比较。根因、触发链或主要修复目标实质相同，即使标题不同或旧单已关闭，也按重复跳过。不以标题精确匹配或 GitHub 搜索结果替代完整语义去重。
3. 同一轮候选之间也要语义去重。指纹只用于辅助定位，不替代语义判断。
4. 跳过已修复、已有防护消除问题，或缺少明确代码依据的候选；不因缺少动态复现直接剔除。
5. 按用户影响、触发可能性、证据强度和修复可执行性排序，最多保留 3 个。
6. 在正式创建阶段开始前，刷新并完整分页核对远端 Issue；随后每次创建前检查该完整基线之后的新建或更新 Issue，并纳入本轮已创建结果。若无法确认去重基线完整，停止创建。

## 五、Issue 草案和无写入预检

Issue 使用中文，标题格式：

`【Bug Request】<对象或场景 + 具体错误行为>`

正文格式：

```markdown
## 一、问题描述

建议级别：<严重 或 一般/低级>

现象：...
触发条件：...
期望结果：...
实际结果：...
用户影响：...
分析或复现：<代码推导，或实际运行的复现结果；未运行时明确注明>

## 二、相关配置

- 入口：...
- 相关调用关系：<简要说明>
- 代码证据：`path/to/file:line`，`function_or_method`
- 源码链接：<固定提交 SHA 的 GitHub 文件行链接>
- 分析提交：<SHA>
- 相关环境/配置：...

## 三、修复建议

- 根因：...
- 建议改法：<针对已确认根因的具体改法>
- 回归验证：...
```

为每个候选根据规范化的“仓库、文件、函数、根因、触发条件”计算 SHA-256 指纹，以 HTML 注释形式附在正文末尾：

`<!-- auto-bug-fingerprint: <sha256> -->`

将最终标题、正文和两个标签组成 JSON 请求体，保存在临时目录。进行一次简单、不产生远端写入的 dry-run，确认 JSON 可提交、正文能说明问题且去重完成即可；不设置额外验证清单。这里的 dry-run 是本地预检，不是 GitHub API 的参数，也不需要任何外部脚本。

预检通过后必须进入正式创建；草案或 dry-run 通过不等于完成任务。

## 六、直接调用 GitHub API 正式创建

仅使用以下两个标签，不添加 `bug`、分类、优先级或其他状态标签：

| 标签 | 颜色 | 描述 |
|---|---|---|
| auto-generated | 5E0BDB | Generated by automated repository inspection |
| needs-triage | FFF403 | Waiting for issue triage |

1. 分别查询两个标签是否存在。只在确认 404 表示标签不存在时，使用 `POST /repos/{owner}/{repo}/labels` 创建缺失标签，不修改已有标签。其他错误不得当作不存在处理。
2. 完成正式创建前的再次语义去重，确认预检后草案没有变化。
3. 对每个通过检查的候选实际执行 `POST /repos/{owner}/{repo}/issues`，提交：

   ```json
   {
     "title": "【Bug Request】具体标题",
     "body": "完整中文正文及指纹注释",
     "labels": ["auto-generated", "needs-triage"]
   }
   ```

4. 正常创建应返回 HTTP 201，并包含 `number` 和 `html_url`。记录返回结果；不得自行编造编号或链接。
5. POST 超时、连接中断或返回结果不确定时，禁止盲目重发。先查询远端，通过指纹、标题和正文确认是否已经创建；无法确认时停止该候选并报告“创建结果不确定”。GitHub 创建 Issue API 不应被假定具有自动幂等能力。
6. 对明确失败的请求报告经过脱敏的状态码和原因。单个候选不合格或重复只跳过该候选；鉴权失败、API 全局故障、请求预算耗尽或必需标签无法准备时停止后续写入。

## 七、远端复核与完成标准

创建后调用 `GET /repos/{owner}/{repo}/issues/{issue_number}`，确认目标仓库中已存在该 Issue，内容与草案一致，两个流程标签正确，并记录真实编号和链接。

只有真实创建并完成远端复核才算成功交接。若远端标签受其他自动化影响出现差异，记录“不完整创建”，不要反复覆盖其他节点的标签。所有未通过的复核项必须明确报告。

不创建或修改 `.ci/`，不要求本地持久化记录。远端 Issue、正文指纹和最终报告承担结果记录及跨轮次去重用途。

## 八、最终输出

最终只输出以下执行结果，不输出冗长思考过程、凭证或无关日志：

```markdown
## 执行结果

- 自动化任务：临时自动化，问题发现
- 目标仓库：S-zhi/ThirdBrain
- 分析提交：<SHA 或未取得及原因>
- 探索方式：只读源码探索
- 预算使用：<实际耗时>/30 分钟；API 请求 <N>/100 次
- 初步候选：N；深入分析：N
- 通过准入：N（严重 X，一般/低级 Y）
- 远端已确认创建：N；复核通过：N；不完整创建：N
- 创建结果不确定：N
- 重复跳过：N；其他剔除：N

## 已创建 Issue

1. #编号 [标题](链接)
   - 级别：...
   - 远端最终标签：...
   - 核心证据：`文件:行号`，函数/方法名
   - 复核状态：通过 或 不完整创建及原因

无已确认创建项时写“无”，不得把草案列为已创建。

## 未创建项

- 候选标题或标识：具体跳过、剔除或失败原因；重复项附已有 Issue 链接。
- 结果不确定项单独标明，不归入确认成功或确认失败。

## 异常

- 无；或写明失败阶段、已经完成、尚未完成及建议处理方式。
```

实际创建数少于 3 时，明确说明“没有为了凑数降低标准”。完成检查但没有合格新候选时，写“本轮未发现满足准入标准且未被记录的新 Bug”。若因全局故障或预算限制未完成检查，应写明“检查未完成，不能据此判断没有新 Bug”，不得将未检查误报为未发现。
