# GitHub PR 自动合并提示词

## 头部：任务综述

请完成自动化任务：`【S-zhi/ThirdBrain】自动合并（GH1-步骤4）`。

你负责将 GitHub 仓库 `S-zhi/ThirdBrain` 中带有 `Pass` 标签的 open PR 合并到各自的目标分支。`Pass` 表示审核已通过，以该标签作为准入依据，无需重新检查审核评论或发起评审。

流程为：`Pass → 尝试合并 → 解决代码冲突并推送 → 再次尝试合并`。冲突修复后直接推送原 PR 分支，不额外运行测试，不重新评审。最多尝试 `3` 轮（含首次，默认共 3 轮）；仍失败则添加 `merge-failed` 并结束本轮。

执行前完整阅读正文和尾部装饰器。每次只处理一个 PR，选定后不切换。

# 第一部分：执行规范

## 1. 准入与操作范围

- 只选择 `S-zhi/ThirdBrain` 中带有 `Pass` 且不带 `merge-failed` 的 open PR，按创建时间从早到晚选择一个。
- 允许读取 PR、相关 Issue、代码和仓库规则；解决冲突、提交并推送原 PR 分支；通过 GitHub 合并接口完成合并。
- 允许在失败终止时为选中 PR 添加 `merge-failed`，标签缺失时创建；不修改其他流程标签，不删除分支，不提交审核，不执行测试、构建或额外质量检查。
- 合并方式使用 `merge`，目标分支以 PR 当前 base 分支为准，不固定为 main。
- 每次推送和合并前重新确认 PR 仍为 open、仍带 `Pass`，且源分支和目标分支未被更换。`Pass` 被移除或 PR 关闭时停止；已合并则确认成功。

## 2. 鉴权与工作区

`GITHUB_PERSONAL_ACCESS_TOKEN` 是保存 GitHub PAT 的环境变量名称，不是 PAT 值。名称须符合 `[A-Za-z_][A-Za-z0-9_]*`，通过环境读取接口取得值，禁止使用 eval。

仅向 GitHub 子进程或认证请求提供凭证，不打印、不写入文件、不放入提交或评论。变量不存在或为空时报告阻塞。

使用独立临时 checkout 或 worktree处理选中 PR，保留用户已有工作区改动。读取适用的仓库指令。不得强推、重置共享分支、绕过分支保护或直接推送目标分支。完成合并使用 GitHub 合并接口。

## 3. 冲突解决逻辑

确认失败确实由代码冲突导致后，拉取最新目标分支和 PR 分支，将目标分支合入 PR 分支，在原 PR 分支上解决冲突。

逐个比较共同祖先、目标分支和 PR 的内容，保留目标分支的新改动及 PR 的功能意图：

- 不同位置或独立逻辑的修改合并保留。
- 同一逻辑的修改结合上下文整合，必要时同步调整相关调用者和接口。
- 删除与修改、重命名与修改冲突，检查引用和功能用途后决定迁移、保留或删除。
- 依赖锁文件先解决依赖声明，再使用仓库对应工具生成一致结果；不借机升级无关依赖或执行测试。
- 不允许对全部冲突机械使用 ours/theirs，不夹带无关重构。

解决后仅检查 Git 是否仍存在未合并索引项、是否遗留本轮冲突标记，以及 diff 是否限于同步目标分支和解决冲突。这些是提交完整性检查，不运行测试、构建或额外质量检查。随后提交并直接推送原 PR 分支，再次尝试合并。

如果无法从代码与 PR 意图确定冲突的正确处理方式，记录具体文件和待决定事项，不用任意取舍伪造解决。

## 4. 重试规则

合并失败不一定是代码冲突，先读取 GitHub 或 Git 返回的实际原因：

- **代码冲突**：进入冲突修复、提交、推送、重新合并循环。
- **目标分支更新**：重新获取最新分支，再尝试合并；出现冲突时修复。
- **PR 分支被其他人更新**：重新获取并整合远端提交，不覆盖他人工作、不强推。
- **临时锁、合并状态计算中、网络故障或限流**：从 `40` 秒开始退避重试，遵守服务端 Retry-After；等待时定期检查 PR 状态。
- **本地 Git 锁**：确认锁路径及持有进程。活动进程持锁时等待；只允许清理本任务隔离目录内、已确认无持有进程的遗留锁，不删除其他目录或来源不明的锁。
- **仓库要求的自动检查尚在运行**：等待现有检查，不主动启动测试。
- **权限不足、检查明确失败、必须重新审批、分支策略禁止合并、无权推送源分支或冲突意图无法确定**：报告阻塞，不绕过策略，也不重复执行必然失败的请求。

每轮尝试包含状态读取、必要的冲突修复与推送，以及合并请求；因锁、修复失败或网络故障未能发出合并请求，也计为一轮失败。最多执行 `3` 轮，包含首次尝试，禁止在轮内另设无限重试或等待。每次命令使用超时。

达到上限或遇到明确不可恢复的阻塞时，重新读取 PR：已合并则报告成功；仍为 open 且带 Pass 时添加 `merge-failed` 并确认写入成功，保留其他标签，然后结束本轮，不改选其他 PR。后续查询排除 `merge-failed`；只有该标签被人工或其他流程移除后，才重新进入自动合并队列。标签写入失败时明确报告，不能声称已标记。

# 第二部分：执行 Pipeline

## Phase 1：查询 Pass PR 并尝试合并

1. 完成鉴权，分页查询目标仓库的 `is:pr is:open label:Pass -label:merge-failed`，按创建时间排序并选定最早一个。初始化尝试计数为 0，每进入一轮尝试先加 1。
2. 读取其 head SHA、源仓库与分支、目标分支及当前合并状态。
3. 使用 `merge` 尝试合并，提交 expected head SHA，防止误合并未读取的新版本。
4. 成功则进入结果确认；失败则按实际原因进入冲突修复或等待重试。

## Phase 2：修复冲突并直接推送

1. 在隔离工作区获取最新目标分支和 PR 分支，将目标分支合入 PR 分支。
2. 按冲突解决逻辑处理全部冲突。
3. 完成提交完整性检查后直接提交并推送，不运行测试、不重新评审。
4. 重新读取远端 head SHA 和 `Pass` 状态，回到 Phase 1 的合并操作。

只在尝试次数未达到 `3` 时重复上述循环。达到上限仍失败则按重试规则添加 `merge-failed` 并结束；出现明确阻塞则提前执行失败处理。请求超时后先查询实际结果，避免重复推送或误报失败。

## Phase 3：确认并按需输出

重新读取 PR，只有 GitHub 确认已合并才报告成功：

```text
已合并：<PR 编号、标题和链接>
冲突处理：无冲突 / 已修复并推送
```

没有符合条件的 PR 时只输出：

```text
本次未合并
```

尝试耗尽或阻塞时简要输出 PR 链接、已尝试次数、失败原因及 `merge-failed` 是否添加成功。不要把失败或执行中断表述为“没有候选”。

# 尾部：执行装饰器（执行前必须阅读）

本节补充前述规则，模板内部冲突时以本节为准。后续调优规则追加于本节。

## 完成检查

- [ ] 选中的 PR 属于目标仓库且带有 `Pass`。
- [ ] 失败原因已区分为代码冲突、可重试故障或明确阻塞。
- [ ] 冲突修复兼顾目标分支和 PR 的功能意图。
- [ ] 冲突修复已直接推送原 PR 分支，没有强推。
- [ ] 没有运行测试、构建或发起重新评审。
- [ ] 总尝试次数未超过 `3`，没有绕过仓库合并策略。
- [ ] 尝试耗尽后已添加并确认 `merge-failed`，或明确报告标签写入失败。
- [ ] 已从 GitHub 确认最终合并状态后再输出。

清单按实际发生的操作核对，未发生的冲突修复等步骤视为不适用，无需输出空报告。
