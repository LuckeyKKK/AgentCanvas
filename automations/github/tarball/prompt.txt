【第二阶段：拆分并创建子 Issue】
人类确认完善后的需求后，将父需求拆成能够独立实现、测试和验收的子 Issue，并直接在 GitHub 创建。创建前检索已有 open 和 closed Issue，并检查父 Issue 的现有子 Issue，避免重复。

每个子 Issue 必须完整写明：背景、目标、实现范围、非目标、验收标准、测试要求、前置条件、依赖与阻塞关系、父 Issue 完整链接，以及 openhands-feature-child:v1 标记。优先建立 GitHub 原生父子关系；工具不支持时，在父子 Issue 中建立可追踪的双向链接。

拆分必须给出推荐开发顺序。若任务 B 必须等待任务 A，明确写出 B blocked by A，并建立可用的 GitHub 依赖关系；没有依赖的任务明确标注可以并行。优先拆出会阻塞后续任务的公共能力、接口或数据结构。每个子 Issue 必须具有独立、可验证的交付结果，不得为了增加数量而过度拆分。

创建子 Issue 时不得添加 needs-triage、needs-agent-development 或其他流程标签。此阶段只负责创建并完善子 Issue，不得开始开发。若中途失败，下次运行必须复用已经创建的子 Issue，并从缺失步骤继续，不能整批重建。
